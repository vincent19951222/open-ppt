# Page-by-page Markdown content draft

Read this reference when creating a new presentation, before writing slides. Follow the approval stage in [the creation workflow](workflows/create.md), step2a.

## Draft requirements

- Save a real `outline.md` file in the intended project directory, not just a chat summary. Use the user's requested presentation language.
- State the deck topic, audience, purpose, and exact proposed page count. Note the presentation duration and style/template only when known or useful; do not add a questionnaire for optional details.
- Give each page a sequential, stable label (`Page 01`, `Page 02`, etc.), a topic/communication goal, the actual slide title, and the complete intended on-slide body copy. Include every planned page, including cover, dividers, and closing pages. The declared total must match the page sections.
- Write the copy the user will actually review: use complete bullet points, explanations, table entries, or diagram labels as appropriate. “Discuss the advantages here” is an instruction, not slide content. A cover may have a subtitle and presenter/date instead of body bullets. Do not add speaker notes unless requested.
- For charts and tables, include the values, units, comparisons, and source needed to check the message. For diagrams, specify the nodes, labels, and relationships. For images, describe the intended subject and its purpose; slide-image generation can wait until approval.
- Cite supplied materials by file/page/section and researched facts with original-source links and dates or periods where applicable. Clearly label missing information and assumptions; never fabricate data to fill the draft.
- Keep proposed visuals and layout suggestions separate from the on-slide copy. Mark optional fields as not applicable or omit them when they add no value.
- List unresolved questions in one place and refer to the affected pages. If the material is insufficient, make the gap visible so the user can review what needs supplying.

## Example structure

Adapt the fields to the content; this two-page example illustrates the review format, not a required deck length. The example contains no measured business claims.

```markdown
# 客户支持知识库建设方案｜逐页内容稿

- 受众：客户支持团队负责人
- 目的：确认知识库试点范围与实施步骤
- 总页数：2 页（含封面）
- 状态：待用户审查

## Page 01｜方案介绍

### 页面主题
说明本次方案讨论的对象与目标。

### 页面标题
客户支持知识库建设方案

### 正文内容
副标题：试点范围、实施步骤与验收方式

### 图表或图片建议
无，使用文字封面。

## Page 02｜试点实施步骤

### 页面主题
说明从资料整理到试点验收的执行顺序。

### 页面标题
先完成资料核对，再开展小范围试用

### 正文内容
1. 整理资料：汇总现有帮助文档和常见问题清单。
2. 核对内容：由业务负责人确认答案准确性和适用范围。
3. 开展试用：选择一个支持小组试用，并记录缺失和错误答案。
4. 复核结果：修正问题，依据双方确认的标准决定是否扩大使用。

### 图表或图片建议
四步流程图：整理资料 → 核对内容 → 开展试用 → 复核结果。

### 来源与依据
本页为拟议实施步骤，供审查，不代表已经完成的工作。

## 待确认项
- Page 02：试点小组与验收标准尚待确定。
```

## Review and handoff

Deliver the file link and ask the user to review page count, page topics, copy, and unresolved items. Stop at this stage until the user explicitly approves, unless an exception in the creation workflow step2a applies. When revising, update the draft and its review status; after approval, mark it approved and retain it with the final project. If the user explicitly skips review, record that review was skipped rather than claiming approval.
